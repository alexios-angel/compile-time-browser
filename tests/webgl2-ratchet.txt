# THE LADDER IS COMPLETE (2026-08-02). It started at ZERO the same day:
# `getContext('webgl2')` returned null by an explicit decision, so rung 1 was
# where it stopped and everything above was unmeasured rather than failing.
#
# RUNG 9 WAS NEVER A WEBGL PROBLEM. Babylon asks for webgl2 first and settles on
# version 2 here, but it could not be compiled at all until GENERATORS existed -
# 622 `function*` bodies, none of them an author writing a generator:
# TypeScript compiles every `async` function into one driven by an `__awaiter`
# helper, so `yield` in that bundle is what `await` became. See docs/script.md.
#
# WHAT THE THREE CORPORA SAY, measured rather than assumed:
#
#   p5.js      asks for webgl2 FIRST and falls back silently - so everything
#              ever proven about its WEBGL mode here was proven on the fallback
#   Phaser     never asks at all; it takes VAOs and instancing from WebGL 1
#              extensions, and gets null for all of them today
#   Babylon    asks for webgl2 and uses nearly the whole specification - UBOs,
#              3D textures, MRT, transform feedback, queries, sync, samplers -
#              gating 52 sites on _webGLVersion so it degrades cleanly
#
# WHAT RUNG 8 COST, kept because four defects had to fall for it and each was
# invisible from JavaScript. Phaser's WEBGL renderer initialises, boots and runs
# create(); getting from there to a painted pixel needed, in order:
#
#   bufferSubData             did not exist
#   TRIANGLE_STRIP / FAN      refused - and STRIP is Phaser's DEFAULT topology
#   a fresh VAO's attributes  an EMPTY table, so every vertexAttribPointer after
#                             binding one was dropped by its own bounds guard
#   typed arrays              owned values instead of viewing bytes, so four
#                             views over one ArrayBuffer were the same object
#
# Not one of them raised a GL error or threw. The whole class is "a silent no-op
# that leaves the canvas black", which is why every step below was measured
# inside the engine rather than inferred from what the page could see.
#
# THE TRACE THAT FOUND THE LAST ONE, since the method is the reusable part.
# Phaser's draws reached the rasteriser
# with six vertices and shaders that compile and link; `inPosition` is bound at
# location 0 from buffer 13, size 2, float, stride 12, offset 0 - all correct -
# and 288 bytes are uploaded to that buffer by bufferSubData every frame. Those
# 288 bytes are ALL ZERO, and they are zero before they ever reach C++.
#
# Phaser's WebGLBufferWrapper.createViews makes FOUR views over one ArrayBuffer
# - Float32Array, Uint8Array, Uint16Array, Uint32Array - and writes vertex
# positions through the F32 one. A typed array here OWNS its elements as
# `value`s rather than viewing bytes, so all four views are handed the SAME
# array_object and each `new` overwrites its element kind. The last view wins,
# the shared storage ends up u32, and every float written afterwards is coerced
# to an integer. Read back as float, 64 becomes 9e-44, which is zero to any
# question the rasteriser asks.
#
# The fix, landed: a typed array VIEWS bytes rather than owning values. The
# ArrayBuffer holds them and each view carries its own (kind, offset, length)
# over them. That also removed the RangeError builtins.cpp used to throw for
# `new Uint8Array(buf, offset, length)`, which existed for the same reason - an
# offset view could not be expressed while a view owned its elements.
#
# Two wrong diagnoses, recorded because both cost a day:
#
#   1. `drawElements` answering INVALID_OPERATION. It never does. That reading
#      came from wrapping every gl method in JS and calling getError() after
#      each - which ATTRIBUTES A STALE ERROR to the first wrapped call, because
#      getError returns the first error since it was last asked.
#   2. "Phaser paints 2048 fragments, so the renderer works." Those 2048
#      fragments are rungs 5-7's own test page, not Phaser: the DIAG output was
#      read without checking which context it came from. Phaser paints ZERO.
#
# The VAO defect found on the way is worth its own note, because it is the one
# a future VAO change is most likely to reintroduce. A fresh gl_vertex_array
# default-constructed its attribute table EMPTY while the context sized its own
# to 16 slots, and binding SWAPS the live table - so binding a new VAO installed
# a zero-slot table, after which every enableVertexAttribArray and
# vertexAttribPointer was dropped by its own bounds guard and every draw
# gathered no attributes. Phaser reaches VAOs only through
# OES_vertex_array_object, so it hit this the moment rung 7 made the extension
# real: rung 7 going green is what broke rung 8.
#
# RUNG 9 IS BABYLON, and it is blocked on something with nothing to do with
# WebGL: 622 `function*` and 803 `yield` in the bundle, from TypeScript's
# __awaiter transpilation. Generators are a VM feature - suspending and resuming
# a frame - and the machinery for it already half exists, because `await` on an
# unsettled promise saves a frame into a coroutine object (see heap_kind::
# coroutine in script/value.hpp). That is the decision rung 9 waits on, and it
# should be taken on its own merits rather than as a step in this plan.

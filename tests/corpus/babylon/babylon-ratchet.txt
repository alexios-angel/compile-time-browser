# How much of a Babylon.js SCENE this engine can render.
# tests/babylon_ratchet.cpp measures it; this file records it. The level may not
# go DOWN, and at the same level the blocker may not CHANGE, without the test
# failing.
#
# Only tools/babylon-ratchet.py --advance writes this file. A test that edits its
# own expectations cannot fail, so advancing is a deliberate act.
#
# The ladder: 1 a scene renders, 2 a texture samples, 3 two meshes with two
# materials, 4 an animation moves the picture, 5 a directional light shades,
# 6 specular, 7 alpha blending, 8 a post-process runs, 9 a shadow lands, 10 PBR,
# 11 glTF import, 12 the GUI.
#
# IT STARTS WHERE tests/corpus/webgl2/webgl2-ratchet.txt STOPS. That ladder asks whether
# Babylon draws AT ALL and reads 10/10; this one asks what a scene can CONTAIN.
#
# EVERY RUNG ASKS THE CANVAS, and that is not a stylistic choice. `isReady()`,
# `material.isReady()` and "did it throw" all answered YES for weeks while the
# canvas showed nothing but the clear colour. A Babylon feature that is missing
# here fails SILENTLY from JavaScript - that is the character of this corpus.

level=10
blocker=not measured yet - glTF import and the GUI need corpus additions, see docs/babylon-plan.md

# 9 -> 10 ON A MISSING DOM METHOD, and it was never a graphics problem.
#
# `document.removeEventListener` did not exist. The window had both halves and
# an element had both; the document could only ADD. Babylon's PBR path gates
# readiness on an environment BRDF texture decoded from a base64 PNG, and the
# cleanup in that image's load callback threw
# "`removeEventListener` is undefined, not a function".
#
# WHAT IT LOOKED LIKE was "a PBR material painted 0 pixels" - a renderer
# failure, three layers from a DOM gap. The fault was reported at all only
# because note_callback_fault exists; before that it would have been a callback
# that silently stopped.
#
# The comment beside the ELEMENT's removeEventListener claimed the window and
# the document could both already do this. Half of that was untrue and had been
# since it was written. It is corrected in place.
#
# THE LADDER IS NOW AT ITS ENGINE CEILING. Rungs 11 and 12 are glTF import and
# the GUI, and both need bundles that are not vendored - babylonjs-loaders and
# babylon.gui.js. That is a corpus decision, not an engine one, and
# docs/babylon-plan.md has said so from the start.
#
# ONE ESTIMATE WORTH DISTRUSTING NEXT TIME: a session was planned for opening up
# texImage2D so a depth texture could be allocated, on the reasoning that
# WebGL 2 forces ShadowGenerator down createDepthStencilTexture. The reasoning
# is correct and rungs 8, 9 and 10 all passed without any of it.

# 7 -> 9 ON ONE TABLE ENTRY, and the number is the least interesting part.
#
# `TEXTURE_BINDING_3D` was in no constant table here. Babylon picks the GLSL
# dialect it emits from whether that property EXISTS -
# `_webGLVersion: e.TEXTURE_BINDING_3D ? 2 : 1` - so it concluded WebGL 1 and
# prepended no `#version` to anything, while its shader PROCESSOR read the
# engine's own version, correctly saw 2, and rewrote every body to ES 3.00.
#
# Fragment shaders survived: the processor injects `layout(location = 0)` and
# this engine's repair keys on `layout(`. `postprocessVertexShader` has none,
# so it was parsed as ESSL 1.00, rejected, and the fullscreen quad never drew -
# leaving the canvas exactly as the clear left it, with NO GL ERROR. That is
# why rung 8 looked like a post-process bug for four days.
#
# RUNG 9 CAME FREE WITH IT. A whole session was budgeted for the shadow on the
# reasoning that WebGL 2 forces `createDepthStencilTexture` and this engine's
# texImage2D cannot allocate a depth format. That reasoning is still true and
# the shadow lands anyway. The estimate was wrong; the measurement was one run.
#
# THE RECORD WAS ALSO STALE, which is worth knowing before trusting a number
# here: level 8 was earned on 2026-08-03 against the software rasteriser, which
# was deleted 24 hours later. Rung 8 had never passed on ANGLE at all, so the
# "regression" was a comparison against a backend that no longer existed.
#
# Rung 10 is now blocked on something small and specific: PBR gates readiness on
# an environment BRDF texture loaded from a base64 PNG data URL, and the image
# load path throws because `removeEventListener` does not exist.

# 7/12 ON THE SECOND READING, and one engine bug did most of it.
#
# THE BUG: `drawArrays` set a texture sampler on its draw request and
# `drawElements` DID NOT. Every INDEXED draw therefore sampled (0, 0, 0, 1) -
# black - however correct the texture was, and an indexed draw is what a mesh
# is. A hand-written `drawArrays` quad sampled a texture perfectly through the
# same context, which is what made this look like a Babylon problem rather than
# an engine one for a while. There is ONE sampler now, shared by both paths:
# two copies of one job is the shape this tree has paid for three times, with
# two URL parsers, two base64 decoders and now two sampler callbacks.
#
# AND `ArrayBuffer.isView`, which did not exist. One missing standard-library
# method, and PBRMaterial and PBRMetallicRoughnessMaterial both threw in their
# constructors - the whole physically-based path unreachable.
#
# TWO OF THE FOUR RUNGS THAT MOVED WERE MY OWN MISTAKES, recorded because the
# next reader will write rungs too:
#
#   RUNG 2 SET emissiveColor TO WHITE and expected a green box. Babylon's
#   shader says `emissiveColor += texture(emissiveSampler, uv).rgb * ...` - it
#   ADDS - so white saturates to white whether the texture sampled or not, and
#   the rung read the same before and after the fix. It sets BLACK now, so the
#   texture is the only thing that can colour the box.
#
#   RUNG 4 COUNTED PAINTED PIXELS to see an animation move. A rotation
#   PRESERVES AREA: the box had turned 0.38 radians and the count had moved by
#   16 pixels out of 592. It compares the pixels themselves now (picture::digest),
#   which is what "the picture changed" actually means.
#
# WHAT PASSES NOW: a scene renders, a texture samples, two meshes with two
# materials, an animation moves the picture, A DIRECTIONAL LIGHT SHADES (two
# distinct shades on a turned box, which is what says the normal matrix
# arrived), SPECULAR (a highlight brighter than the diffuse term), and ALPHA
# BLENDING (a colour with both channels, which no opaque draw here can make).
#
# RUNG 8 PASSES: a post-process runs, and it took RENDER-TO-TEXTURE, which did
# not exist. `bindFramebuffer` recorded an id and changed nothing, so a scene
# drawn "into a texture" went to the CANVAS and whatever sampled that texture
# afterwards read an empty one. Babylon's IDENTITY post-process - a pass that
# copies the frame and changes nothing - turned a working scene into a black
# canvas that way, with no GL error and `checkFramebufferStatus` answering
# COMPLETE unconditionally, which is a lie a page acts on.
#
# THREE THINGS HAD TO BE TRUE AT ONCE and each hid the next:
#
#   `framebufferTexture2D` was a no-op, so no framebuffer had an attachment.
#
#   `bindFramebuffer` read its argument with `as_number` while a framebuffer
#   arrives as a WRAPPED OBJECT like every other GL object - so it bound ZERO
#   every time. That was invisible while framebufferTexture2D did nothing, and
#   became an INVALID_OPERATION the moment it stopped being a no-op.
#
#   A framebuffer needs its OWN depth buffer, swapped in with it. A shadow map
#   is a different size from the window, and sharing the canvas's depth compares
#   a fragment against a neighbour's - the same class of bug as sharing an
#   attribute table across vertex arrays, which this tree has paid for once.
#
# An INCOMPLETE framebuffer now draws NOWHERE rather than to the canvas, which
# is what GL does and is much better than drawing to the wrong surface.
#
# RUNG 9 IS THE SHADOW, and it has been narrowed to one line. The box is there
# in two shades of red and THE GROUND IS NOT DRAWN AT ALL - 3220 of 4096 pixels
# are still the clear colour - so this is not "the shadow is missing", it is
# "the surface the shadow would fall on never arrived".
#
# ISOLATED, four scenes, one variable at a time:
#
#   ground alone, unlit                    3060 white pixels - fine
#   ground lit by a directional light      3060 at 250,250,250 - fine
#   ground + receiveShadows, NO generator  3060 at 250,250,250 - fine
#   the same + a ShadowGenerator           the ground is GONE
#
# So `receiveShadows` alone is harmless and the SHADOW GENERATOR is what breaks
# the ground's draw. A generator makes Babylon add its shadow defines to that
# material and recompile it, so the next thing to look at is whether that
# recompiled shader RUNS - a shader that fails at run time has its draw dropped
# with INVALID_OPERATION, which paints exactly nothing and is what this looks
# like. Not the shadow map's contents, and not the render target, which rung 8
# now exercises.

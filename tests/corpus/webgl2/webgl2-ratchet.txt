# measures it; this file records it. The level may not go DOWN, and at the same
# level the blocker may not CHANGE, without the test failing.
#
# Only tools/corpus/webgl2-ratchet.py --advance writes this file. A test that edits its
# own expectations cannot fail, so advancing is a deliberate act.
#
# The ladder: 1 a webgl2 context, 2 the WebGL 2 constants, 3 #version 300 es
# compiles, 4 vertex array objects, 5 instanced drawing accepted, 6 an instanced
# draw reaches the pixels, 7 the same capability under its WebGL 1 extension
# names, 8 Phaser's own WebGL renderer paints on it, 9 Babylon runs and reports
# its WebGL version, 10 Babylon renders a scene to the pixels.
#
# RUNG 7 IS THE DESIGN DECISION MADE CHECKABLE. docs/history/webgl2.md commits to
# ONE implementation of VAOs and instancing exposed under TWO spellings, because
# Phaser reaches them only through the WebGL 1 extensions and would otherwise
# never touch the code the WebGL 2 rungs prove. If 6 passes and 7 fails, there
# are two implementations - the bug this tree has already paid for twice, with
# two URL parsers and two base64 decoders.

# RUNG 10 WAS ADDED THE DAY RUNG 9 WENT GREEN, because 9 turned out to ask too
# little: it built a BABYLON.Engine and read `webGLVersion`, which a bundle can
# answer without ever drawing. Running is not rendering. Rung 10 builds the
# smallest real scene - a camera, a light and a box - and asks the canvas.
#
# WHERE IT STOPS, and the reading is precise: Babylon's CLEAR reaches the pixels
# (the canvas is the blue it cleared to) and its GEOMETRY does not (the centre
# is that same blue, so the box is not there). Draws do reach the rasteriser -
# 40 of them, 4096 fragments each, which is the whole 64x64 canvas - so this is
# not "nothing runs", it is "the geometry shades to the background". That is the
# next thing to chase and it is a much narrower question than the one rung 9
# left.
#
# WHAT RUNG 10 COST SO FAR, and where it now stands. Four things were wrong and
# two of them were this engine's:
#
#   getShaderPrecisionFormat   NOT IMPLEMENTED, so Babylon's capability probe
#                              decided the engine has no high-precision floats
#                              and took its lower-precision paths. It returns
#                              IEEE single now, because that is literally what
#                              raster/glsl_eval.cpp computes in.
#   deleteShader               ERASED THE SHADER. `glDeleteShader` only FLAGS an
#                              object; one attached to a program lives until the
#                              program does, which is why compile-attach-link-
#                              delete is the universal idiom. Babylon does
#                              exactly that, and it cost 119 refused draws a
#                              frame: the program linked, the material reported
#                              ready, and every drawElements failed on a program
#                              whose shaders had evaporated.
#   the probe rendered once    Babylon processes shader code through PROMISES,
#                              so an effect is never ready in the turn the
#                              material is created. One scene.render() renders
#                              nothing and can never render anything however
#                              correct the engine is. It registers a render loop
#                              and runs 120 frames now, which is what a page
#                              does - and readiness went false -> true.
#   THE VENDORED BUNDLE        is the current blocker and is NOT an engine bug.
#
# WHERE IT STOPS. Babylon links a program whose vertex shader is 1388 bytes of
# `#define` lines and NO BODY - it parses to zero interface variables, so there
# are no attribute locations, so Babylon never calls vertexAttribPointer, so
# every vertex gathers as zero and 119 draws a frame paint nothing. The reason
# is the first line of the file we vendored:
#
#   function _BabylonUMDDynamicImportUnsupported() {
#     return Promise.reject(new Error("Dynamic import of a module specifier is
#     not supported in the UMD/global Babylon build; use the ES module build"))
#
# The UMD build fetches StandardMaterial's shader body by dynamic import and
# rejects its own request. 58 `gl_Position` occurrences are in the bundle, so
# some shaders ship; the default material's does not.
#
# SO THE NEXT STEP IS ES MODULES, and it has its own plan now:
# docs/plans/modules.md. The alternative - vendor a different Babylon build and
# hope its shaders are inlined - is the shim this tree was told not to build.
# Babylon ships as modules first and a UMD bundle as a courtesy, and that
# courtesy is what rung 10 currently depends on.
#
# THE PROBE HAD TO BE FIXED BEFORE IT COULD SAY THAT. It first cleared to BLACK
# and asked for any non-black pixel, which makes "painted nothing" and "painted
# black" the same reading - two different findings with two different next
# steps. Clearing to blue separated them. Then it asked only for a non-black
# pixel, which the blue clear satisfies on its own: that version passed while
# the box was missing entirely. It now requires the CENTRE and the CORNER to
# differ, which is the assertion that actually means "geometry drew".
#
# THE LADDER'S FIRST NINE RUNGS ARE COMPLETE (2026-08-02). It started at ZERO the same day:
# `getContext('webgl2')` returned null by an explicit decision, so rung 1 was
# where it stopped and everything above was unmeasured rather than failing.
#
# RUNG 9 WAS NEVER A WEBGL PROBLEM. Babylon asks for webgl2 first and settles on
# version 2 here, but it could not be compiled at all until GENERATORS existed -
# 622 `function*` bodies, none of them an author writing a generator:
# TypeScript compiles every `async` function into one driven by an `__awaiter`
# helper, so `yield` in that bundle is what `await` became. See docs/script.md.
#
# WHAT THE THREE CORPORA SAY, measured rather than assumed:
#
#   p5.js      asks for webgl2 FIRST and falls back silently - so everything
#              ever proven about its WEBGL mode here was proven on the fallback
#   Phaser     never asks at all; it takes VAOs and instancing from WebGL 1
#              extensions, and gets null for all of them today
#   Babylon    asks for webgl2 and uses nearly the whole specification - UBOs,
#              3D textures, MRT, transform feedback, queries, sync, samplers -
#              gating 52 sites on _webGLVersion so it degrades cleanly
#
# WHAT RUNG 8 COST, kept because four defects had to fall for it and each was
# invisible from JavaScript. Phaser's WEBGL renderer initialises, boots and runs
# create(); getting from there to a painted pixel needed, in order:
#
#   bufferSubData             did not exist
#   TRIANGLE_STRIP / FAN      refused - and STRIP is Phaser's DEFAULT topology
#   a fresh VAO's attributes  an EMPTY table, so every vertexAttribPointer after
#                             binding one was dropped by its own bounds guard
#   typed arrays              owned values instead of viewing bytes, so four
#                             views over one ArrayBuffer were the same object
#
# Not one of them raised a GL error or threw. The whole class is "a silent no-op
# that leaves the canvas black", which is why every step below was measured
# inside the engine rather than inferred from what the page could see.
#
# THE TRACE THAT FOUND THE LAST ONE, since the method is the reusable part.
# Phaser's draws reached the rasteriser
# with six vertices and shaders that compile and link; `inPosition` is bound at
# location 0 from buffer 13, size 2, float, stride 12, offset 0 - all correct -
# and 288 bytes are uploaded to that buffer by bufferSubData every frame. Those
# 288 bytes are ALL ZERO, and they are zero before they ever reach C++.
#
# Phaser's WebGLBufferWrapper.createViews makes FOUR views over one ArrayBuffer
# - Float32Array, Uint8Array, Uint16Array, Uint32Array - and writes vertex
# positions through the F32 one. A typed array here OWNS its elements as
# `value`s rather than viewing bytes, so all four views are handed the SAME
# array_object and each `new` overwrites its element kind. The last view wins,
# the shared storage ends up u32, and every float written afterwards is coerced
# to an integer. Read back as float, 64 becomes 9e-44, which is zero to any
# question the rasteriser asks.
#
# The fix, landed: a typed array VIEWS bytes rather than owning values. The
# ArrayBuffer holds them and each view carries its own (kind, offset, length)
# over them. That also removed the RangeError builtins.cpp used to throw for
# `new Uint8Array(buf, offset, length)`, which existed for the same reason - an
# offset view could not be expressed while a view owned its elements.
#
# Two wrong diagnoses, recorded because both cost a day:
#
#   1. `drawElements` answering INVALID_OPERATION. It never does. That reading
#      came from wrapping every gl method in JS and calling getError() after
#      each - which ATTRIBUTES A STALE ERROR to the first wrapped call, because
#      getError returns the first error since it was last asked.
#   2. "Phaser paints 2048 fragments, so the renderer works." Those 2048
#      fragments are rungs 5-7's own test page, not Phaser: the DIAG output was
#      read without checking which context it came from. Phaser paints ZERO.
#
# The VAO defect found on the way is worth its own note, because it is the one
# a future VAO change is most likely to reintroduce. A fresh gl_vertex_array
# default-constructed its attribute table EMPTY while the context sized its own
# to 16 slots, and binding SWAPS the live table - so binding a new VAO installed
# a zero-slot table, after which every enableVertexAttribArray and
# vertexAttribPointer was dropped by its own bounds guard and every draw
# gathered no attributes. Phaser reaches VAOs only through
# OES_vertex_array_object, so it hit this the moment rung 7 made the extension
# real: rung 7 going green is what broke rung 8.
#
# RUNG 10 IS GREEN: Babylon renders a scene to the pixels. 1444 of the 4096 are
# the box, at 255,128,128 - emissive red plus half white, which is a hemispheric
# light on a face whose normal is perpendicular to it. The number being RIGHT
# rather than merely non-background is what says the uniforms arrived.
#
# FOUR THINGS WERE WRONG, and they were in series: each was invisible until the
# one before it was fixed, and not one of them raised an error.
#
#   1. `String.prototype.search` DID NOT EXIST. Babylon's shader processor calls
#      it on every shader it compiles. The call rejected a promise nobody
#      surfaces, the processed source stayed empty, and every material compiled a
#      program out of its `#define` lines alone - 1388 bytes with no body. One
#      missing string method, and a whole renderer draws nothing.
#
#   2. THE SHADERS THEN DID NOT COMPILE: `layout(...)` qualifiers, `uniform
#      Material { ... }` blocks, `uint` and the `1u` suffix. A block's members
#      are declared as ordinary uniforms when it has no instance name, and as a
#      STRUCT when it has one, because those are the two ways the body refers to
#      them. `uint` is mapped onto `int` and the limit is written down rather
#      than hidden.
#
#   3. UNIFORM BUFFER OBJECTS WERE REFUSED BY NAME. That was a deliberate
#      scoping decision in docs/history/webgl2.md and it was the wrong one: WebGL 2
#      delivers uniforms through buffers and Babylon uses them for everything the
#      moment it sees a WebGL 2 context. Refused, its shaders linked, its draws
#      were issued, and every matrix read as ZERO - a scene collapsed to a point
#      on a canvas showing exactly the colour it was cleared to. `bindBuffer`
#      also sent UNIFORM_BUFFER to the array-buffer binding, so filling a
#      uniform buffer overwrote whichever vertex buffer was bound.
#
#   4. A STRUCT UNIFORM ARRIVED WITHOUT ITS TYPE. The environment hands over
#      floats and cannot know which entry of a shader's struct table the type is
#      - the same value is read by both shaders and their tables differ - so the
#      declared type is put back on read. The map that does it lives in
#      prepared_state: `prepare` runs on one interpreter and every draw runs on
#      a fresh one, so anything built by build_globals and not carried across is
#      silently empty at run time. It was, and the error read "`.vLightDiffuse`
#      is not a field of struct", which is true and useless.
#
# AND A WRONG DIAGNOSIS THAT SAT IN THIS FILE FOR WEEKS, corrected here because
# it sent two sessions the wrong way: rung 10 was NOT blocked on the UMD build
# rejecting its own dynamic `import()`. That call is an HTML-in-canvas polyfill
# loader and has nothing to do with drawing - Babylon's shaders come out of its
# own ShaderStore, which was fully populated the whole time. The reading came
# from finding `_BabylonUMDDynamicImportUnsupported` in the bundle and the empty
# shader source in the same session, and connecting them.
#
# HOW THE CHAIN WAS ACTUALLY FOUND, since the method is the reusable part: wrap
# every method on the gl object from JS, DRAIN getError before each call and read
# it after, and record the first call that errors. The record above warns that
# getError attributes a stale error to the wrong call - draining first is what
# makes it sound. That one probe named `getUniformBlockIndex`,
# `uniformBlockBinding`, `bindBufferBase` and `drawElements` in a single run.
#
# Then, for the failures that raise NOTHING: ask whether the code AFTER the
# suspect point ran. `_rawVertexSourceCode` was 5705 bytes and
# `_vertexSourceCode` was empty, which located the fault between them without
# knowing anything about Babylon's internals.
